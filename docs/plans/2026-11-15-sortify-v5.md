# Sortify v5 Implementation Plan

Goal: implement the approved next-update requirements in docs/NEXT_UPDATE.md.
Architecture: one native Go helper owns configuration, classification, duplicate
comparison, journaled file transfers, locks, service scheduling and Undo. Shell
entry points select the correct binary and forward a strictly data-only JSON
protocol. A local HTML/CSS/JS WebUI uses the KernelSU callback bridge; desktop
preview is explicitly labeled and never pretends to have device access.
Tech stack: Go standard library, Android shell, dependency-free WebUI, Python/Node
for development verification only. No Go/Python runtime is required on the phone.

## Constraints

- Keep id=sortify, prepare version 5.0/versionCode 11; do not publish update.json
  until release assets are available. No commit/push/release without instruction.
- Fresh installations: auto off, hourly interval, one-day delay on; preserve v4
  interval and automatic behavior on upgrade with an explicit migration notice.
- The two supplied reference images define the editorial light WebUI, with an
  xCaptaiN09 footer. All assets work offline.
- Prefer a branch in the freshly cloned checkout; retain existing requirements.

## Tasks and contracts

1. Core (internal/engine): write failing behavior tests, implement Settings,
   Category, Rule, Snapshot and the JSON request API; temporary-dir storage tests.
   Commands: snapshot, settings.save {settings}, preview, start, stop,
   undo {runId, entryId?}, holds.release {path}, history.clear,
   settings.export, settings.import {settings}. Responses: {ok,data,error}.
   Settings keys: schema, autoSort, intervalSeconds, delayEnabled,
   source, destination, historyDays, categories:[{id,name,enabled,extensions,
   destination}], rules:[{id,name,enabled,pattern,category}], ignore:[glob],
   unknownFiles:'others'|'leave'. Defaults: historyDays 30, interval range
   60..604800, fixed 24h optional organization delay, 60s minimum stability.
   Snapshot: {version,settings,status,history,holds,warnings}; status includes
   running, stopping, serviceRunning, lastRun, nextRun, currentFile, error.
   Preview: {items:[{source,destination,category,outcome,reason,duplicateOf,
   matchingRules,winner}],summary,warnings}; history runs include id,startedAt,
   finishedAt,state,summary,entries. Times are Unix seconds; summary counts
   moved,duplicates,renamed,skipped,failed. Outcomes: move,duplicate,skip,error.
   Run entries include id,source,destination,category,outcome,reason,duplicateOf,
   time,undone. Native helper accepts --state DIR --storage DIR --module DIR;
   request BASE64_JSON and serve/run/undo modes. Invalid input must change no files.
2. WebUI (webroot): separate bridge.js, app.js, style.css, index.html; implement all
   controls using the contract, native DOM textContent for untrusted filenames.
   Async bridge returns parsed envelopes; wait for actual shell exit status.
   Background start returns quickly; snapshots report progress. Provide an
   explicitly labeled desktop demo adapter only on ?demo=1.
3. Integration: shell lifecycle migration, native binary packaging/build scripts,
   release assembly and metadata checks, README/changelog, meaningful regression
   tests. Default request command: sh /data/adb/modules/sortify/sortify.sh request
   BASE64. stdin-free base64 request size is bounded; CLI supports file/stdin input
   separately for developer tests/export. Bundled ARM64, ARMv7, x86_64 and x86
   binaries are built from the same source for Android-compatible execution.
4. Review and verify: native unit/race tests, file-system integration tests,
   shell syntax, WebUI interactions/mobile screenshots, release ZIP verification.
   Test adversarial filenames, repeated duplicate collisions, hash equality,
   exclusions, changing files, two operations, stale processes, failed copy,
   atomic settings, stop, preview, history retention, Undo and hold persistence.
   Record device verification limits explicitly; no Android device is attached.

## Execution record

- Plan created before implementation. Broader architectural requirements were
  approved in conversation; remaining routine choices settled here.
- Go helper selected because implementing JSON, stable identities and exclusive
  destination creation in shell would be brittle. Static native binaries preserve
  the root-module deployment without an interpreter dependency.
- Use task agents for the independent core and WebUI, followed by integration and
  a separate review. Each agent writes behavior tests before implementation.
